# Общедомовой бот: заявки, объявления и диспетчеризация

Бот на aiogram 3 + PostgreSQL. Общего чата нет: только заявки жителей, маршрутизация исполнителям по категориям и объявления от диспетчера.

## Роли

### Житель

Житель может:

* подавать заявки;
* видеть статус своих заявок;
* читать объявления.

Регистрация выполняется самостоятельно через `/start`. Пользователь указывает номер квартиры и ФИО, но получает статус подтверждённого жителя только после одобрения диспетчером.

### Исполнитель

Исполнитель привязан к одной из категорий:

* электрик;
* сантехник;
* охрана.
* клининг;
* Казахдомофон.

Он может переключать статус «на смене», принимать заявки своей категории и завершать их с результатом «выполнено» или «не выполнено».

### Диспетчер

Диспетчер может:

* видеть все заявки;
* назначать и переназначать исполнителей вручную;
* подтверждать жителей;
* добавлять исполнителей;
* публиковать объявления.

Первые диспетчеры задаются в `.env` через `ADMIN_IDS`.

### Председатель

Председатель — это пользовательское название существующей внутренней роли
`administrator`, а не отдельная роль. Он наследует все возможности диспетчера,
согласовывает заявки Казахдомофон, управляет объявлениями и отчётами и может
отозвать доступ участника без удаления истории.

### Специальные категории

Заявки Казахдомофон создаются из трёх готовых вариантов: Face ID, добавление
камер и изготовление магнитов. Для Face ID обязательна фотография. До
согласования председателем заявка не видна исполнителю; отклонение закрывает её
с обязательным комментарием.

Для клининга житель отправляет фото или видео с описанием места. Вне графика
(пн–пт 08:00–13:00, сб 08:00–12:00, вс выходной) заявка переносится на начало
следующего рабочего интервала, а житель получает автоматическое двуязычное
сообщение. Официальные праздники отдельно не учитываются.

Для сантехника и электрика житель выбирает работу внутри квартиры либо в МОП.
При выборе квартиры бот автоматически показывает двуязычное уведомление о
платном характере работ.

Свой `telegram_id` можно узнать у `@userinfobot`. При первом `/start` пользователь с ID из `ADMIN_IDS` автоматически получает роль диспетчера.

## Маршрутизация заявок

Житель создаёт заявку, после чего она получает статус `new`.

Уведомление отправляется исполнителям нужной категории, которые сейчас находятся «на смене».

Если на смене никого нет, уведомление сразу отправляется всем исполнителям этой категории, чтобы заявка не осталась без внимания.

Первый исполнитель, который нажал «Принять», получает заявку. Захват выполняется атомарно через:

```sql
UPDATE ...
WHERE status = 'new'
```

Логика находится в `services.claim_request`.

Поэтому даже если два исполнителя одновременно нажмут «Принять», заявку получит только один. Второй увидит сообщение, что она уже принята другим исполнителем.

Если заявку никто не принял за `ESCALATION_MINUTES`, по умолчанию 20 минут, `scheduler.py` повторно рассылает её:

* всем исполнителям соответствующей категории независимо от статуса смены;
* диспетчеру.

Диспетчер в любой момент может принудительно назначить или переназначить исполнителя из карточки заявки в разделе «Все заявки». Это работает независимо от того, была ли заявка уже принята через самозахват.

## Что проверено

Логика ролей и маршрутизации протестирована локально. Для тестирования использовалась SQLite как временная база данных.

Проверены:

* создание заявки;
* одновременная попытка двух исполнителей забрать одну заявку;
* атомарный захват заявки, при котором только один исполнитель получает `True`;
* принудительное переназначение исполнителя диспетчером;
* импорт всех модулей без ошибок при установленных зависимостях.

Использованные зависимости:

* aiogram 3.15;
* SQLAlchemy 2.0;
* asyncpg;
* APScheduler.

## Что не проверено

Для следующих проверок нужен реальный токен бота и работа через Telegram:

* фактическая отправка сообщений;
* поведение UI-кнопок в Telegram-клиенте.

## Что стоит доработать перед продакшеном

### FSM-хранилище

Сейчас используется `MemoryStorage`. После перезапуска бота незавершённые диалоги сбрасываются. Например, пользователь потеряет прогресс, если остановится посередине создания заявки.

Для продакшена стоит использовать `RedisStorage` из `aiogram.fsm.storage.redis`.

### Миграции базы данных

Сейчас `init_db()` вызывает `create_all`, что подходит для первоначального создания схемы.

Дальнейшие изменения структуры базы данных лучше выполнять через Alembic.

### Список заявок диспетчера

Сейчас отображаются последние 20 заявок без пагинации и фильтров.

Если бот используется в доме на 500 и более квартир и поток заявок становится большим, стоит добавить:

* пагинацию;
* фильтрацию по статусу;
* фильтрацию по категории.

При необходимости можно сделать небольшую веб-админку поверх той же базы данных.

### Логирование и мониторинг

Сейчас используется только базовый `logging.basicConfig`.

Для продакшена стоит добавить централизованный сбор ошибок, например Sentry.

### Резервное копирование

Для такого объёма данных достаточно ежедневного резервного копирования PostgreSQL.
